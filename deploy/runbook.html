01

Create the droplet

In the DigitalOcean console: Create → Droplets.

  • Region — Bangalore (BLR1). This is the whole reason for choosing a droplet over Vercel: it is far closer to Shillong than Singapore.
  • Image — Ubuntu 24.04 (LTS) x64
  • Type — Basic → Regular → 2 GB RAM / 1 vCPU / $12
  • Authentication — SSH key, not password. Paste your ~/.ssh/id_ed25519.pub; if you have no key, create one with ssh-keygen -t ed25519.
  • Hostname — iyka-web

Do not take the $6 droplet

Building this app needs roughly 2 GB of memory. On the 1 GB box the Next build is killed by the kernel partway through, and the error it leaves behind looks nothing like an out-of-memory problem. Step 5 adds swap as a second safety net.

Note the IPv4 address once it finishes provisioning. It appears below as DROPLET_IP.

02

First login and updates

from your laptop
$ ssh root@DROPLET_IP

# apt update && apt upgrade -y
# apt install -y curl git ufw

If the upgrade replaces the kernel it may ask about restarting services — accept the defaults, then reboot with reboot and log back in after a minute.

03

Create the deploy user

The site should not run as root. This user owns the code and the process; it gets exactly one sudo privilege, to restart its own service.

as root
# adduser --disabled-password --gecos "" iyka

# # carry your SSH key over so you can log in directly
# mkdir -p /home/iyka/.ssh
# cp /root/.ssh/authorized_keys /home/iyka/.ssh/
# chown -R iyka:iyka /home/iyka/.ssh
# chmod 700 /home/iyka/.ssh && chmod 600 /home/iyka/.ssh/authorized_keys

# # one narrow sudo right, so deploy.sh can restart the app unattended
# echo 'iyka ALL=(ALL) NOPASSWD: /bin/systemctl restart iyka-web' \
      > /etc/sudoers.d/iyka-web
# chmod 440 /etc/sudoers.d/iyka-web
# visudo -c

visudo -c must print parsed OK. A malformed sudoers file can lock you out of sudo entirely, so never skip that check.

04

Close the firewall

as root
# ufw allow OpenSSH
# ufw allow 'Nginx Full'
# ufw enable
# ufw status

Order matters

Allow OpenSSH before ufw enable. Reversed, the firewall comes up denying port 22 and closes your own connection — recoverable only through the DigitalOcean web console.

Port 3000 is deliberately absent. Next binds to 127.0.0.1 only and is reachable exclusively through nginx.

05

Add swap

2 GB of RAM builds this app, but without much headroom. Swap turns a hard out-of-memory kill into a slow build, which is a far better failure.

as root
# fallocate -l 2G /swapfile
# chmod 600 /swapfile
# mkswap /swapfile && swapon /swapfile
# echo '/swapfile none swap sw 0 0' >> /etc/fstab

# # prefer RAM; only reach for swap under real pressure
# sysctl vm.swappiness=10
# echo 'vm.swappiness=10' >> /etc/sysctl.conf
# free -h
06

Install Node, nginx and certbot

Next 16 requires Node ≥ 20.9. Ubuntu's own package is older, so take it from NodeSource.

as root
# curl -fsSL https://deb.nodesource.com/setup_22.x | bash -
# apt install -y nodejs nginx certbot python3-certbot-nginx

# node -v   # expect v22.x
# npm -v
07

Clone the repository

as root, then as iyka
# mkdir -p /srv/iyka-web && chown iyka:iyka /srv/iyka-web
# su - iyka

$ git clone https://github.com/marksheridan/IYKA-ARAM.git /srv/iyka-web
$ cd /srv/iyka-web && git log -1 --oneline

If the repository is private

HTTPS cloning will prompt for credentials the server cannot supply. Generate a key on the droplet with ssh-keygen -t ed25519 -C iyka-droplet, add the public half to the repo under Settings → Deploy keys (read-only is enough), and clone the git@github.com:… URL instead.

08

Put the secrets in place

as iyka
$ cp /srv/iyka-web/deploy/env.production.example /srv/iyka-web/.env
$ chmod 600 /srv/iyka-web/.env
$ nano /srv/iyka-web/.env

The template lists every variable with a note on where its value comes from. For Phase 1 the ones that matter are:

VariableValue
SMTP_USERThe clinic mailbox — yonawellnessandhealthcare@gmail.com, not a personal account
SMTP_PASSA 16-character Google App Password generated on that account
MAIL_TOSame clinic address — it mails itself
ADMIN_PASSWORDBackoffice password
ADMIN_SECRETopenssl rand -base64 32
DATABASE_URLNeon connection string. Unused by Phase 1 pages, still wanted by /api/health

No credentials, no bookings

With SMTP_PASS empty the site still works and still accepts enquiries — but it prints them to the system journal instead of emailing anyone. Nobody at the clinic finds out, and patient phone numbers accumulate in the logs in plain text. Fill this in before announcing the site.

09

First install and build

as iyka
$ cd /srv/iyka-web
$ npm ci
$ npm run build

The build takes two to four minutes on this box. It downloads the Google font files during the build, so the droplet needs outbound internet access. It should end with the route table and no /booking, /store or /blog surprises. Confirm it runs before going further:

as iyka
$ npm start &
$ curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/
$ kill %1

A 200 means the app is sound and everything after this is plumbing.

10

Run it as a service

systemd keeps the site up across crashes and reboots. The unit is committed at deploy/iyka-web.service.

as root
# cp /srv/iyka-web/deploy/iyka-web.service /etc/systemd/system/
# systemctl daemon-reload
# systemctl enable --now iyka-web
# systemctl status iyka-web --no-pager

Expect active (running). Live logs — including simulated enquiry emails while SMTP is unset — come from:

as root
# journalctl -u iyka-web -f
11

Put nginx in front

as root
# cp /srv/iyka-web/deploy/nginx.conf /etc/nginx/sites-available/iyka-aram
# ln -s /etc/nginx/sites-available/iyka-aram /etc/nginx/sites-enabled/
# rm -f /etc/nginx/sites-enabled/default

# # nginx reads the static files directly, so it needs to traverse the path
# chmod o+x /srv /srv/iyka-web

# nginx -t && systemctl reload nginx

The one line that carries security weight

The supplied config sets proxy_set_header X-Forwarded-For $remote_addr; — set, not append. Most nginx examples use $proxy_add_x_forwarded_for, which adds to whatever the caller sent. Under that version, anyone can put a fabricated address in front of the chain, land in a fresh rate-limit bucket on every request, and walk straight past the per-IP limits on the booking form. $remote_addr is the real TCP peer and cannot be forged.

The reasoning is recorded in src/app/(site)/actions.ts beside the code that depends on it. If you ever put Cloudflare in front of this droplet, revisit both — with a CDN in the path, every visitor arrives as the CDN's address instead.

The site should now answer on http://DROPLET_IP.

12

Point the domain

At your registrar for iyka-aram.com, create two A records:

TypeHostValue
A@DROPLET_IP
AwwwDROPLET_IP

Wait for it to propagate before attempting the certificate — Let's Encrypt validates by fetching over HTTP, and fails if DNS has not caught up.

from your laptop
$ dig +short iyka-aram.com

This domain is baked into the build

sitemap.xml and robots.txt are generated from business.url in src/content/site.ts, which is set to https://iyka-aram.com. Deploy under any other hostname and the sitemap will advertise URLs that do not resolve.

13

Turn on HTTPS

as root
# certbot --nginx -d iyka-aram.com -d www.iyka-aram.com
# systemctl status certbot.timer --no-pager

Choose redirect-to-HTTPS when asked. Certbot edits the site config in place, adding the TLS block and the redirect. Renewal is automatic through certbot.timer; confirm it works without waiting ninety days:

as root
# certbot renew --dry-run
14

Verify what shipped

Phase 1 is a narrow surface on purpose. These are the states to confirm:

URLExpected
/ /about /services /products200
/gallery /podcast /contact200
/booking404 — deleted, not hidden
/store /blog307 → / (gated)
/admin307 → /admin/login
/mis307 → /login
POST /api/orders404 JSON

Then the part no script can check for you: open the live site, submit the Book a consultation pop-up, and confirm the email arrives in the clinic inbox. Submit twice more with the same number — the third should be refused with "We've already received your enquiry." That single test exercises the whole Phase 1 pipeline: form, validation, rate limiting, SMTP.

→

Deploying again, after this

Every later deploy is one command from your laptop:

from your laptop
$ ssh iyka@DROPLET_IP '/srv/iyka-web/deploy/deploy.sh'

It fetches origin/main, runs npm ci and the build, restarts the service, and then polls until the site actually answers — printing the last forty log lines and exiting non-zero if it does not. A failed deploy tells you so rather than leaving you guessing.

The site is unreachable for the two or three seconds systemd takes to restart. Removing that blink means running two ports and switching nginx between them; for a clinic brochure site it is not worth the complexity.

→

When Phase 2 arrives

The store and blog are already built and already on the server — they are held shut by environment variables, not missing code. Opening them is four edits and a deploy:

  • Set STORE_LIVE="true" and BLOG_LIVE="true" in /srv/iyka-web/.env
  • Confirm DATABASE_URL points at a live Neon database
  • Restore the two links in src/components/site/site-footer.tsx — the comment there names them exactly
  • Drop /store and /blog from the disallow list in src/app/robots.ts

Then redeploy. If you would rather host Postgres on this droplet than pay for Neon, that is a reasonable call at this scale — but it makes database backups your responsibility, and an unbacked-up clinic database is a worse problem than a monthly bill.

Config files live in deploy/ on main: nginx.conf, iyka-web.service, deploy.sh, env.production.example. Edit them in the repo rather than on the server, so the next deploy does not quietly overwrite a fix you made in place.
